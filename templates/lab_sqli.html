🧠 Why this worked
{% if mode == "vuln" %}

In vulnerable mode, user input is directly inserted into the SQL query.

The query structure looks like this:

        SELECT username, role FROM lab_users WHERE username = 'USER_INPUT'

When you entered a payload like: 

        admin' --

The input closed the original string and used -- to ignore the rest of the statement. This allowed the database to return unintended results.

{% if lab_variant == "sqli" %}

Another common beginner payload is:

        ' OR '1'='1

This makes the WHERE condition always TRUE, so the database returns a user even if the input is incorrect.

{% endif %}

This is called SQL Injection — when user input changes the logic of a database query.

{% if lab_variant == "sqli_admin" %}

In this challenge, the goal is more specific: you must manipulate the query so that it returns the admin user.

This simulates a real-world privilege escalation, where an attacker bypasses authentication to gain administrative access.

{% endif %}
{% else %}

In secure mode, the query uses a placeholder: 

        SELECT username, role FROM lab_users WHERE username = ?

The user input is treated strictly as data, not executable SQL.

Even if special characters or SQL keywords are entered, they cannot modify the structure of the query.

Because the SQL structure is fixed, SQL Injection attacks are prevented.

{% endif %}
🛡 How it’s fixed

Secure applications use parameterized queries.

Parameterized queries separate:

  • SQL structure
  • User input data

Since user input is handled only as data, it cannot change the logic of the SQL statement.
